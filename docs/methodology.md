# 数学研究の自動化: 本リポジトリの方法論

「AI に数学の未解決問題を解かせる」を、再現可能な工程に落とすための覚書。
調べたベストプラクティスと、実際に p0000〜p0003 を回して分かったことを混ぜて書く。

## 0. 出発点: 2026 年のヤコビアン予想の反例

2026 年 7 月 19 日、3 変数の明示的な多項式写像としてヤコビアン予想の反例が公表された
(`p0000_jacobian_2026` の `survey` に出典)。この事例が方法論として重要なのは、
**結果が有限の対象 1 個に落ちている**点である。反例写像 $F$ さえあれば、

* ヤコビ行列式が 0 でない定数であること
* $F$ が単射でないこと

は誰でも独立に確かめられる。探索がどれほど巨大でも、検証は小さい。
逆に言えば、**この形に落ちない結果は自動化に向かない**。本リポジトリは
「有限証明書に落ちる問題だけを扱う」という制約を最初に置いている。

## 1. 五つの設計原則 (README と対応)

1. **主張は有限証明書に落とす。** 結果は「対象 (JSON)」と「検証手続き」の 2 つ組。
   浮動小数点数は証明書に入れない (整数・有理数・代数的数のみ)。
2. **検証器は探索器と実装を共有しない。** `mar.checkgraph` は標準ライブラリだけで
   書き、`mar.search` を import しない。アルゴリズムも意図的に変える
   (探索: 分枝限定 / 検証: 極大独立集合の全列挙、探索: マッチングの分枝 /
   検証: 線グラフへの還元)。共通のバグが両方をすり抜ける確率を下げるため。
   **定数も共有しない**: 「$n \le 10$ の連結グラフを全部読んだ」の根拠になる
   OEIS の公表値は、検証器が自分の表 (`checkgraph.PUBLISHED_*`) を持つ。
   探索器が書いた期待値と突き合わせると「探索器の表に探索器の出力が一致した」
   という無内容な検査になる。
3. **先行研究ゲート。** `Problem.survey.evidence` が空なら `mar search` は動かない。
   計算探索の最大の失敗は誤りではなく**既知の結果の再発見**である。
4. **検証に落ちた証明書は論文化しない。** `mar paper` は verify を再実行する。
5. **数値は本文に直書きしない。** 論文本文は証明書 JSON から生成する。
   人手で書いた数字と計算結果がずれる事故を構造的に潰す。

## 2. テーマ選定

自動化が効くのは次の条件を満たす問題である。

| 条件 | 理由 |
|------|------|
| 反例が有限の対象 1 個 | 反証が「見つけて渡す」だけで閉じる |
| 対象の完全リストが第三者から公開されている | 網羅性の根拠を自前の同型判定に依存しない |
| 不等式が**片側** | 証人つき検証 (§3) が使える |
| 未解決性の出典が明示できる | 原則 3 のゲートを通せる |

実際に使った素材:

* **TxGraffiti の予想リスト** (arXiv:2507.17780)。自動予想生成系が出した予想が
  「未解決」「解決済み」のラベル付きで並んでおり、原則 3 のゲートを通しやすい。
  p0001 (予想 3)、p0002 (予想 2)、p0003 (予想 4) はここから採った。
* **B. McKay の組合せデータ** (連結グラフ・木の完全リスト)、**GENREG** (正則グラフ)。
  「$n \le 10$ の連結グラフを全部見た」の根拠を OEIS の公表個数との突合で示せる。

避けるべき素材: 解析的な評価だけで閉じる主張、無限族の構成、
「十分大きい $n$ で成立」型の主張。有限証明書に落ちない。

## 3. 証人つき検証 (witness-based certificate)

本リポジトリで一番効いた工夫。$Z(G)$ (ゼロ強制数)、$\alpha(G)$ (独立数)、
$\mu^*(G)$ (飽和数) はいずれも計算が NP 困難で、素朴に
「探索器の計算を検証器がやり直す」と検証コストが探索コストと同じになる。
だが**片側の不等式**なら、証人を渡せば検証は線形時間になる。

| 主張 | 証人 | 検証器がやること |
|------|------|-----------------|
| $Z(G) \le \alpha(G)+1$ | 独立集合 $A$ と ゼロ強制集合 $S$ ($\lvert S\rvert \le \lvert A\rvert+1$) | 独立性の判定 + 強制過程の実行 |
| $\mu^*(G) \le H(G)$ | 極大マッチング $M$ ($\lvert M\rvert \le H(G)$) | 極大性の判定 + 次数の和 |

$\alpha(G) \ge \lvert A\rvert$ と $Z(G) \le \lvert S\rvert$ は定義から従うので、
NP 困難な最適化を検証器が解き直す必要がない。探索器がどんな発見的手法を
使ったかは検証に無関係で、嘘をつけば「証人が条件を満たさない」で落ちる。

**逆向きは閉じない。** 「反例である」「等号が成立する」は下界を要するので、
証人だけでは検証できない。ここで「大きい族は探索器を信用する」と書いてしまうと、
検証済みに見えて実は未検証の数字が論文に載る。避けるための型が 2 つある。

### 例外リスト方式 (p0002 の等号分類)

逆向きが必要になる対象を**漏れなく列挙して証明書に載せる**。検証器は

* リストに載ったものだけ厳密に再計算する ($Z = \alpha+1$ を確かめる)、
* 載っていないものは証人が**より強い**条件を満たすことを確かめる
  ($|S| \le |A|$、これで $Z \le \alpha$ が片側に閉じる)

の 2 つを行う。後者は線形時間なので、族が何万個あっても分類全体が閉じる。
NP 困難な計算を検証器が解くのは例外の個数 (p0002 では 46 個) だけ。
探索器が例外を隠せば、隠されたグラフで $|S| \le |A|$ が破れて検出される。

### 上下から挟む方式 (p0003 の最大比)

「族内の $\max \mu^*/H$ は $R$」のような**最大値**の主張は、

* 上から: 証人が各グラフに $\mu^* \le |M|$ を与えるので、
  $\max |M|/H \le R$ を全数について線形時間で確かめれば真の最大値 $\le R$、
* 下から: 最大を達成すると主張されたグラフ 1 個だけ $\mu^*$ を厳密に計算し、
  $\mu^*/H = R$ を確かめれば真の最大値 $\ge R$

の 2 つで確定する。**探索側も同じ不等式で枝刈りできる**のが利点で、
「証人の上界が現在の最大を超えないグラフは最大になり得ない」から、
厳密計算は最大値が小さいうちの数十個で済む。

この設計に切り替える前は、最大比を「厳密計算に進んだグラフ」からしか
集計しておらず、その集合に入らない族で値を取りこぼしていた。
片側評価で足切りした対象を集計に使うときは、**足切りの向きが集計の向きと
合っているか**を必ず確かめる。

どこまでが証人で閉じ、どこからが再計算かは論文の「限界」節に明記する。

### 検証器は「改竄テスト」で担保する

**正しい証明書が通ることは、検証器が何かを検査している証拠にならない。**
何も検査しない検証器でもそれは通る。担保になるのは**嘘の証明書が落ちること**
だけなので、`tests/test_tamper.py` では証明書と証人を実際に書き換えて、
対応する検査項目が FAIL することを確かめる:

* 証人ファイルを 1 バイト反転する → SHA-256 で落ちる
* ハッシュも辻褄を合わせて証人を偽造する → 条件検査 (独立性・極大性) で落ちる
* 等号グラフを 1 個隠す / 等号でないグラフを混ぜる → 例外リスト方式で落ちる
* 最大比を過大にも過小にも書き換える → 上下の挟み込みで落ちる
* 公表値の期待値やグラフ数を偽る → 検証器が独自にもつ表で落ちる

テストは元データの走査量に比例して重くなるので、証明書を小さい族だけに縮めてから
検証器にかける (証人ディレクトリは一時ディレクトリへ差し替える)。

この形のテストは設計の穴も見つける。実際、**最大比を達成するグラフが走査した族の
要素であることを確かめていない**という抜けがここで露見した。証明書が名指しした
graph6 をそのまま厳密計算しても、族外のグラフを持ち出されれば上界と下界が
「別の対象について」一致してしまう。修正は「達成グラフを検証器が走査中に自分で
捕まえ、証明書の名指しと一致することも確かめる」。
**下界の対象は、証明書に書かせるのではなく検証器が選ぶ。**

**実務上の利点**: p0003 では、貪欲な極大マッチングだけで大多数の判定が付き、
厳密計算まで進んだのは全体の数割だった。片側の不等式は「安いヒューリスティクスで
ほとんど片付け、残りにだけ厳密解を使う」設計にできる。

## 4. 証人の置き方

* 族 (位数・種別の組) ごとに 1 本のバイナリファイル (`data/witnesses/`)。
* 元データの**列挙順**に固定長レコードを並べる。検証器は元データを走査しながら
  先頭から消費するので、索引を持たなくてよい。
* ファイルの SHA-256 とレコード数を証明書 JSON に書く。証明書だけが真実の所在。
* 大きい族は gzip で書く (p0003 の $n = 10$ は生 117 MB が 1/10 以下になる)。

## 5. 落とし穴 (実際に踏んだもの)

| 症状 | 原因 | 対策 |
|------|------|------|
| `graph10c.g6` が読めない | McKay のサーバが拡張子なしで gzip 中身を返す | マジックバイト `1f 8b` で判定する (拡張子を信用しない) |
| 検証結果を印字した瞬間に落ちる | Windows の標準出力が cp932 | `sys.stdout.reconfigure(encoding="utf-8")` |
| LaTeX が `Missing $ inserted` | graph6 は `~ ^ _ { } \` を普通に含む | `mar.report.texescape` で一元的にエスケープ |
| f-string で `SyntaxError` | Python 3.10 は f-string 内にバックスラッシュを書けない | LaTeX 断片は先に変数へ組み立てる |
| 1 グラフに 1 分以上かかる | 「$Z \le \alpha$ のゼロ強制集合が存在しない」ことの全探索 | 互いに素なフォートの個数で下界を取り、枝を捨てる |
| 探索は終わったが主張が薄い | 予想の**片側**しか検証していない | 何が証人で閉じ、何が再計算かを最初に決めてから走らせる |
| 検証は通るのに数字が未検証 | 集計 (最大値・分類) を検証器が再計算していない | §3 の 2 つの型で閉じる。閉じないなら論文にそう書く |

最後の 1 行は自分では気づけなかった。**書いたコードは観点別の並列レビューに
かける**こと。ここでは「アルゴリズムの正しさ」と「証明書の健全性・検証器の
独立性」の 2 観点でレビューさせ、後者だけが上の 2 件を検出した。

## 6. 1 問題を回す手順

```
python -m mar survey  pNNNN_xxx    # 未解決性の出典を確認 (ゲート)
python -m mar search  pNNNN_xxx    # 証明書 JSON + 証人ファイルを生成
python -m mar verify  pNNNN_xxx    # 実装を共有しない検証器で再検査
python -m mar paper   pNNNN_xxx    # verify を再実行してから PDF を生成
```

新しい問題を足すときに書くのは 1 モジュール (`problems/pNNNN_*.py`) と
本文ビルダ (`problems/_pNNNN_paper.py`) だけ。前者に `survey` / `search` /
`verify` / `references`、後者に `build(cert) -> {"ABSTRACT", "BODY"}` を書く。
本文中の数値はすべて `cert.data` から生成する (原則 5)。

## 7. 何を「結果」と呼ぶか

有限範囲の網羅検証は**証明ではない**。それでも次の 3 つは価値がある。

1. **反例の非存在範囲** — 「反例があるなら $n \ge 11$」は次の探索の設計を変える。
2. **等号ケースの分類** — 予想の最良性や、証明の際に相手にすべき族が分かる。
3. **反例の完全分類** — すでに反証された予想でも、反例が何個あってどんな形かは
   別の情報である (p0003)。

いずれも論文の主張として書けるが、**証明と同じ強さの主張に見せない**こと。
「限界」節で走査範囲と、証人で閉じていない部分を明示する。
